# Автономный YouTube-стример — дизайн v1

Дата: 2026-08-31
Статус: утверждено, готово к декомпозиции на задачи

## 1. Назначение и скоуп

Сервис в Docker на Linux, который непрерывно стримит локальный плейлист аудиофайлов
на YouTube Live и управляется по REST API. В процессе брейнсторминга скоуп разросся
с исходного MVP из `CLAUDE.md` (concat-demuxer, только start/stop) до полноценного
живого контроля плейлиста без разрыва RTMP-соединения. Concat-demuxer-версия
**не реализуется** — сразу строится FIFO-архитектура.

Функциональность v1:
- Старт/стоп эфира.
- Пауза/резюме (тишина + заставка вместо разрыва RTMP).
- Next/Previous по очереди.
- Воспроизведение конкретного трека по имени (вставляется следующим).
- Скан директории с аудио в каталог треков (по запросу через API).
- Обложка на трек (если нет — дефолтная); конструктор обложек — вне скоупа v1.
- REST API без авторизации, с Swagger/OpenAPI-документацией.
- Одна стрим-сессия одновременно (архитектура не должна делать многосессионность
  невозможной в будущем, но реализуется и тестируется только один сценарий).
- Состояние — только in-memory; при рестарте контейнера эфир обрывается,
  автовосстановление не реализуется.

Вне скоупа v1 (зафиксированные будущие направления, не проектируем сейчас):
- Несколько параллельных стрим-сессий (например, по жанрам).
- Персистентность состояния и автовосстановление эфира после рестарта.
- Конструктор обложек.
- Аутентификация API.

## 2. Архитектура

Компоненты:

- **REST API (Express + TypeScript)** — HTTP-слой: валидация запросов, делегирование
  в `StreamController`. Без авторизации. Документируется через Swagger
  (`swagger-ui-express` + OpenAPI-спецификация).
- **StreamController** — состояние единственной сессии (`idle` / `streaming` /
  `paused` / `error`), управляет жизненным циклом `RtmpPusher`, делегирует команды
  очереди в `PlaylistQueue`.
- **PlaylistQueue** — модель очереди: текущий трек, история (для `previous`),
  список "далее". Поддерживает next/previous/insert-by-name.
- **Library** — каталог треков, построенный сканированием директории (путь к аудио
  → путь к обложке или дефолт). Обновляется только по вызову `/library/rescan`,
  сортировка по имени файла (алфавит).
- **SegmentFeeder** — для каждого элемента очереди запускает короткоживущий
  дочерний ffmpeg-процесс, который транскодирует (аудио + обложка) в MPEG-TS
  сегмент с фиксированными параметрами кодека (h264/aac, одинаковые
  разрешение/fps/sample rate) и пишет байты сегмента в FIFO. Для паузы — сегмент
  "тишина + заставка", зацикленный до `resume`.
- **RtmpPusher** — персистентный ffmpeg-процесс на время сессии: читает FIFO,
  ретранслирует в YouTube RTMP через `-c copy` (без повторного кодирования).

Поток данных:
```
REST → StreamController → PlaylistQueue (что играть дальше)
     → SegmentFeeder (аудио+картинка → TS-сегмент) → FIFO
     → RtmpPusher (-c copy) → YouTube RTMP
```

Переключение трека/пауза реализуются на уровне «что сейчас пишется в FIFO»,
не через перезапуск `RtmpPusher` — поэтому RTMP-соединение с YouTube не рвётся.
MPEG-TS выбран как промежуточный формат, поскольку его сегменты можно
конкатенировать побайтово без пересборки контейнера — стандартный приём для
непрерывных 24/7-стримов.

Ограничение: при `next`/`play-by-name` уже находящиеся в буфере FIFO байты
(обычно до ~64KB, доли секунды аудио) доигрываются перед переключением — это
принятая и осознанная задержка, не баг.

## 3. REST API

| Метод/путь | Действие |
|---|---|
| `POST /stream/start` | Создать FIFO, поднять `RtmpPusher`, начать подачу по текущей `PlaylistQueue` |
| `POST /stream/stop` | Остановить `RtmpPusher` и `SegmentFeeder`, удалить FIFO |
| `POST /stream/pause` | Переключить подачу на сегмент "тишина+заставка" |
| `POST /stream/resume` | Возобновить подачу текущего трека с сохранённой позиции |
| `POST /stream/next` | Прервать текущий сегмент, перейти к следующему треку в очереди |
| `POST /stream/previous` | Перейти к предыдущему треку из истории; на первом треке — идемпотентно остаётся на нём (без ошибки) |
| `POST /stream/play` `{ name }` | Вставить трек по имени следующим в очередь после текущего |
| `GET /stream/status` | Текущее состояние сессии, текущий трек, очередь |
| `POST /library/rescan` | Пересканировать директорию с аудио, обновить каталог |
| `GET /library` | Список доступных треков |

Документация: Swagger UI (`/docs` или аналогично) поверх OpenAPI-спецификации,
описывающей все эндпоинты выше, схемы запросов/ответов и коды ошибок.

## 4. Обработка ошибок и edge cases

- Пустая библиотека при `start` → 409, стрим не запускается.
- Файл трека удалён/повреждён между сканированием и воспроизведением →
  `SegmentFeeder` логирует ошибку, пропускает трек, переходит к следующему
  (единичный плохой файл не должен обрывать эфир).
- `RtmpPusher` неожиданно упал (сеть, невалидный ключ) → сессия переходит в
  `error`; автореконнект не реализуется в v1 — пользователь видит `error` в
  `/stream/status` и должен вызвать `start` заново.
- Трек по имени не найден в `play` → 404.
- Команда несовместима с текущим состоянием (например `next` при `idle`) → 409.
- Повторный `start` при уже активной сессии → 409.
- Обложка отсутствует у трека → используется дефолтная картинка.

## 5. Docker / деплой

- Один образ: Node.js + предустановленный `ffmpeg`.
- Директория с аудио/обложками монтируется volume'ом (read-only).
- `RTMP_URL` и `STREAM_KEY` — обязательные env-переменные, без дефолтов; сервис
  не даёт стартовать стрим без них.
- FIFO создаётся во временной директории контейнера (`/tmp` или tmpfs), не
  переживает рестарт (согласуется с in-memory состоянием).
- Health-check контейнера — `GET /stream/status` отвечает 200 независимо от
  состояния сессии (подтверждает, что процесс жив).

## 6. Тестирование

- Unit-тесты (Jest/Vitest) на чистую логику без реального ffmpeg:
  `PlaylistQueue` (next/previous/insert/порядок), `Library` (мок файловой
  системы), `StreamController` (переходы состояний, валидация недопустимых
  команд).
- `SegmentFeeder`/`RtmpPusher` — обёртки над `child_process.spawn` мокаются в
  unit-тестах.
- REST-слой — тесты через supertest поверх Express-приложения с замоканным
  `StreamController`.
- Ручной/интеграционный smoke-test с реальным ffmpeg и тестовым RTMP-приёмником
  (локальный `nginx-rtmp` или запись в файл вместо YouTube) — не автоматизируется
  в CI на первом этапе.

## 7. Структура проекта

```
src/
  api/            # Express-роуты, контроллеры HTTP, Swagger/OpenAPI
  stream/         # StreamController, состояния сессии
  playlist/       # PlaylistQueue, Library, сканирование
  ffmpeg/         # SegmentFeeder, RtmpPusher, обёртки над spawn
  config/         # чтение env (RTMP_URL, STREAM_KEY, пути)
  index.ts        # bootstrap
test/             # зеркалирует src/
Dockerfile
docker-compose.yml   # опционально, для локального запуска с volume
package.json / tsconfig.json
```
